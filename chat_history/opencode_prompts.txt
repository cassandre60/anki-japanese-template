# PART II — The real development loop

Everything above establishes the project.

Now we enter the **repeating loop**.

This is the core of the whole system.

```text
SELECT READY TASK
        ↓
UNDERSTAND TASK
        ↓
DEFINE SMALL CONTRACT
        ↓
WRITE TEST / CHECK
        ↓
IMPLEMENT
        ↓
LOCAL VERIFICATION
        ↓
DEBUG IF NECESSARY
        ↓
UPDATE STATE
        ↓
COMMIT
        ↓
CI
        ↓
MERGE
        ↓
NEXT READY TASK
```

This repeats dozens or hundreds of times.

That is what was missing from the previous version.

---

# 11. Select the next task

The agent does **not** receive:

> "Build the MVP."

It receives:

> "Work on the next ready task."

The agent reads:

```text
IMPLEMENTATION_PLAN.md
```

and finds a task whose dependencies are complete.

For example:

```text
T3 — Config parser

Status: READY

Dependencies:
T1 complete
T2 complete
```

It becomes the current task.

You don't need to paste the entire development methodology into the prompt every time because the repository itself contains it.

---

# 12. Define the small contract

This is where the video's "small validated bricks" actually enters the workflow.

The agent examines the task and identifies the smallest meaningful contract.

Example:

Task:

> Implement Yomitan definition parser.

Instead of immediately writing the full parser:

```text
HTML
 ↓
parser
 ↓
definition
```

the agent identifies contracts such as:

```text
C1: locate definition node
C2: remove irrelevant nodes
C3: preserve required markup
C4: extract definition text
C5: return normalized representation
```

Now we get:

```text
task
 ↓
small contracts
 ↓
tests
 ↓
implementation
```

That is the practical meaning of a "validated brick."

---

# 13. Write the test for the brick

The agent creates the smallest appropriate test.

Example:

```text
Input:
<div>
  definition
  <style>huge CSS...</style>
</div>

Expected:
definition
```

The test becomes the executable contract.

The important point is:

**this happens before or alongside implementation of the brick, not after the entire feature is completed.**

---

# 14. Implement the brick

The agent now implements only enough code to satisfy the contract.

Then:

```text
small test
    ↓
implementation
    ↓
small test passes
```

Then the next brick:

```text
C1
 ↓
C2
 ↓
C3
 ↓
C4
```

You are progressively constructing the feature from validated components.

---

# 15. What happens to `./verify`?

Now its place is clear.

There are **two levels of verification**.

### Local/inner verification

During implementation:

```text
targeted test
```

answers:

> Does this brick work?

Then increasingly broad checks:

```text
unit tests
integration tests
etc.
```

answer:

> Did my change break related things?

### `./verify`

`./verify` means:

> Run the repository's complete mandatory local quality gate.

Example:

```text
./verify
 ├── formatting
 ├── lint
 ├── static/type analysis
 ├── unit tests
 ├── integration tests
 ├── architecture checks
 └── other mandatory checks
```

An agent should normally run targeted checks while iterating and then `./verify` before declaring the task complete.

That makes the hierarchy:

```text
tiny test
    ↓
targeted test suite
    ↓
./verify
    ↓
CI
```

# 16. Where regression tests fit

Now regression testing has a proper location.

Suppose the parser bug escapes:

```text
<style> leaked into result
```

The agent fixes it.

Then the development loop includes:

```text
BUG
 ↓
diagnose
 ↓
fix
 ↓
add regression test
 ↓
verify
 ↓
commit
```

The regression test becomes part of the permanent repository test suite.

So regression tests are **not a separate phase**.

They're a rule inside the debugging branch of the development loop:

```text
normal development
       ↓
bug discovered
       ↓
fix bug
       ↓
add regression test
       ↓
continue normal development
```

# 17. Completion of a task

Once implementation and verification are successful, the agent updates state.

For example:

```text
IMPLEMENTATION_PLAN.md

Status: COMPLETE
```

The agent may also update technical documentation **only if something actually changed**.

For example:

```text

→ update ARCHITECTURE.md

new invariant introduced
→ update QUALITY.md

new contract introduced
→ update relevant contract/spec

bug fixed
→ add regression test
```

No pointless documentation churn.

# 18. Git happens here

Git is therefore not "step 13."

It is part of the development loop.

```text
task
 ↓
implementation
 ↓
tests
 ↓
./verify
 ↓
commit
 ↓
push
 ↓
CI
 ↓
merge
```

For your solo workflow:

```text
main
│
├── feature/task-123
│
└── feature/task-124
```

Agents work on task branches.

`main` is protected and should remain healthy.

# 19. What should agents do with Git?

I'd give agents permission to:

```text
create branch
commit
push branch
```

but **not automatically merge to main**.

The merge can be your lightweight human control point.

For multiple agents, the rule becomes:

```text
Agent A → branch A
Agent B → branch B
Agent C → branch C
```

Never let five agents independently modify the same working tree.

A shared branch/worktree is an unnecessary source of collisions.

# 20. CI

```text
GitHub
 ↓
CI
 ↓
./verify
 ↓
pass/fail
```

This is the second independent verification layer.

Local verification answers:

> Did the agent's environment pass?

CI answers:

> Does the repository pass in a clean environment?

This catches things such as:

```text

undeclared dependency
platform mismatch
environment-specific issue
generated files missing
```

# 23. Architecture is not frozen

This is crucial.

You don't do:

```text

```

```text

 ↓

 ↓

        ↓

        ↓
```

```text
        ↓
```

# Failure handling lives inside this loop

Don't create another numbered phase.

The development loop branches:

```text
                  TASK
                    │
              implement
                    │
                verify
                    │
           ┌────────┴────────┐
           │                 │
         PASS              FAIL
           │                 │
        finish          diagnose

                 ┌───────────┼───────────┐
                 ↓           ↓           ↓
             code bug   missing test   bad design/spec
                 │           │           │
                 └───────────┴───────────┘
                             ↓
                         fix cause
                             ↓
                       verify again
```

After repeated failure, escalate.

I'd use something like:

```text

agent investigates and fixes

stronger reasoning/debugging model

human decision
```

```text
→ update architecture + migration/task plan

```

That's how the system gets stronger over time.
